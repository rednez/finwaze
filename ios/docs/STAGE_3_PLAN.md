# iOS — План етапу 3 «Запис витрат і доходів (одна валюта)»

> **Статус:** реалізовано, чекає ручної перевірки в симуляторі (крок 9).

Етап 3 з `docs/functional-design.md` (розділ 6): TX-01…08, 10, 11, 13…16, 20, 21, 23, 24, 30 · GEN-01…04, 07…09,
12…14, 19…26. Додатково **TX-12** (перенесено з етапу 7, див. «Рішення»). Залежить від етапу 2.

Результат для користувача: записати витрату чи дохід, побачити її в списку операцій, баланс рахунку в Гаманці
змінюється.

## Рішення

- **Схеми Supabase не змінюються.** Усе будується на тому, що вже використовує web:
  - список — RPC `get_filtered_transactions` (`p_month`, `p_transaction_type`, `p_category_ids`,
    `p_transaction_currency_codes`, `p_account_ids`); сортування й місцевий час (`transacted_at + local_offset`)
    уже на сервері;
  - «чи є взагалі операції» для порожнього стану (`TX-07`) — `select id` з `head: true, count: exact` і
    `type <> 'internal'`, як `getFilteredTransactions` на web;
  - створення — `insert` у `transactions`: `type`, `transacted_at`, `local_offset`, `account_id`, `category_id`,
    `transaction_amount`, `transaction_currency_id`, `charged_amount`, `comment`. Знак суми витрати ставить тригер
    `normalize_expense_amounts_trigger`, валюту списання — `set_charged_currency_trigger`; клієнт шле суми
    додатними (`TX-24`);
  - нова група / категорія — `insert` у `groups` (`name`, `transaction_type`) / `categories` (`name`, `group_id`)
    з `select` рядка у відповідь, як `CategoriesRepository` на web.
- **TX-12 переноситься в етап 3.** Під час реєстрації створюються лише службові група й категорія (`Q-02`), тож без
  створення категорії з пікера новий користувач на iOS не запише жодної операції. Разом із TX-12 — вибір кольору
  з палітри під час створення (частина `CAT-10`; на web діалог з форми операції має лише назву). Зміна кольору
  наявних груп і категорій лишається в етапі 7. Екран «Групи й категорії» (CAT)
  лишається в етапі 7. Таблицю етапів у `docs/functional-design.md` оновити (TX-12 → етап 3).
- **Одна валюта.** Поле «Списано з рахунку» (`TX-22`) — етап 4. До того валюта покупки у витраті **видна, але
  заблокована**: дорівнює валюті рахунку і змінюється разом із рахунком (`TX-21`, `TX-23`). Тож
  `charged_amount = transaction_amount`, `transaction_currency_id` = валюта рахунку. Модель форми вже тримає валюту
  покупки окремо, щоб етап 4 лише відкрив вибір.
- **`local_offset`** — `LocalOffset.current(at: transactedAt).intervalString` (зсув пристрою **на момент операції**,
  а не «зараз» — важливо поблизу переходу на літній час). Показ дати — `formattedTransactionDate(offset:)` зі
  збереженим зсувом (`GEN-12`).
- **Пагінація.** Як на web — весь місяць одним запитом (`p_page_size = NULL`). Лічильник «N записів» — довжина
  списку (`TX-05`); порціями вантажити не потрібно (`Q-07` це лише дозволяє).
- **Фільтри живуть поки працює застосунок** (`TX-08`): `TransactionsViewModel` створюється один раз на сесію
  (тримає `SectionView` / `AppViewModel`), а не в `body` вкладки. Після виходу — скидаються.
- **Оновлення після змін (`GEN-26`).** Після створення операції: список операцій перезавантажується, Гаманець
  перечитує баланси при поверненні (`.task` на появу), `AppViewModel.reloadReferenceData()` — після створення групи
  чи категорії. Ввести простий лічильник змін даних в `AppViewModel` (`dataVersion`), на який підписуються екрани
  через `.task(id:)`, — той самий механізм піде в етапи 4–6.
- **Демо.** `DemoTransactionsRepository` генерує операції місяця за шаблоном web (`TX_DEFS` у
  `src/app/core/services/demo-mode/demo-data.ts`: ті самі дні, категорії, суми, рахунок Main Card / USD), але, на
  відміну від web, **застосовує фільтри локально**, щоб демо показувало їхню роботу. Створення операції, групи й
  категорії — no-op: повертає рядок з `id` 90000 і нічого не зберігає.
- **Натискання на операцію** (`TX-06`): редагування — етап 4, деталі переказу — етап 5; поки без дії (як картка в
  Гаманці на етапі 2). Повний рядок `TX-02` на телефоні не вміщається — показуємо скорочений (дата, категорія,
  сума, коментар одним рядком), решта піде в деталі на етапі 4.

## Кроки

### 1. Модель і дані операцій

- [x] `Features/Transactions/Models`: `Transaction` (id, `transactedAt`, `LocalOffset`, тип, сума операції й
      валюта, сума списання й валюта, курс, рахунок id/назва, група id/назва/колір, категорія id/назва/колір,
      коментар, `transferID`); усі суми `Decimal`.
- [x] `TransactionDto` для рядка `get_filtered_transactions`; `TransactionMapper` (`local_offset` →
      `LocalOffset(interval:)`; нерозпізнаний зсув — помилка мапінгу, а не тихий UTC).
- [x] `TransactionFilters` (місяць, тип, валюта, рахунок, група, категорія) з правилами `TX-04`: зміна валюти
      скидає рахунок, зміна групи скидає категорію; група без категорії → `p_category_ids` = всі категорії групи.
- [x] `TransactionsRepository` (протокол): `transactions(filters:)`, `hasAnyTransactions()`,
      `createExpense(_:)`, `createIncome(_:)`. `SupabaseTransactionsRepository` — як на web.
- [x] `NewTransactionDto` (`Encodable`, суми `Decimal` → JSON-число без `Double`).
- [x] Тести мапера: `NUMERIC` → `Decimal` без втрат, від'ємна витрата, зсув `"-05:30:00"`, колір `nil`.
- [x] Тести фільтрів: параметри RPC для кожної комбінації, дата місяця `YYYY-MM-DD`, скидання за `TX-04`.

### 2. Створення групи й категорії (`TX-12`)

- [x] Демо: обидва методи повертають рядок з `id` 90000, нічого не зберігають.

### 4. Список операцій (`TX-01…08`)

- [x] `TransactionsView` замість заглушки в `SectionView`: панель фільтрів (місяць — вибір місяця з кроком
      «← / →»; решта — `Menu`/`Picker` з «Усі»), лічильник «N записів», дія «Додати» в тулбарі.
- [x] `TransactionRow`: дата й час за місцевим часом операції (`GEN-12`), категорія з кольоровою міткою, група,

- [x] ViewModel живе всю сесію (`TX-08`); скидання при виході.
- [x] Тести ViewModel: стани, порожній стан vs порожній фільтр, скидання фільтрів, повторне завантаження при

### 6. Форма нової операції (`TX-10`, 13…16, 20, 21, 23, 24, 30)

- [x] `TransactionFormViewModel`: тип (Витрата за замовчуванням), рахунок, сума, валюта покупки (= валюта
      рахунку, заблокована), категорія, дата й час (за замовчуванням «зараз»), коментар ≤ 100.
- [x] Валідація (`GEN-21`): рахунок і категорія обов'язкові; сума > 0, ≤ 2 знаки після коми, без знака
      (`GEN-07`); коментар ≤ 100; помилки — після спроби зберегти або зміни поля.
- [x] Введення суми: `TextField` з `.decimalPad`, розбір за локаллю в `Decimal` (кома й крапка), без `Double`.
      Власний `DecimalInputParser` з тестами (`0,1`, `1 250,50`, `12.345` → помилка, `-5` → помилка).
- [x] Запам'ятовування (`TX-16`, `GEN-17`): при відкритті — `DevicePreferences.expenseDefaults` /
      `incomeDefaults`; ідентифікатори, яких уже немає в довідкових даних, ігноруються; після успіху — зберегти
      рахунок, групу, категорію (і валюту для витрати). Перемикання типу підставляє збережене для іншого типу.
- [x] Зміна рахунку скидає валюту покупки на валюту рахунку (`TX-21`).
- [x] «Створити» з індикатором і без повторного натискання (`GEN-20`); успіх → назад до списку, сигнал зміни
      даних (`GEN-26`); помилка → «Не вдалося створити операцію» + текст сервера, форма не очищується (`GEN-19`).
- [x] `NewTransactionView`: сегментований перемикач Витрата / Дохід, поля за `TX-20` / `TX-30`, «Назад» без
      збереження (`NAV-05`). Дата — `DatePicker` дата + час.
- [x] Тести ViewModel: валідація, значення за замовчуванням, запам'ятовування (включно з видаленим рахунком),
      `local_offset` на момент операції, суми додатні в запиті, повторне натискання, помилка.

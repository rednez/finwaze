# iOS — План етапу 7 «Групи й категорії»

> **Статус:** реалізовано; лишилась ручна перевірка частини критеріїв (див. крок 5).

## Контекст

Етап 7 з `docs/functional-design.md` (розділ 6): **CAT-01…12 · GEN-05**. Залежить від етапу 3. Зараз розділ «Групи
й категорії» (меню «…») показує заглушку, а створювати групи й категорії з кольором можна лише з пікера категорій
(`TX-12`, етап 3). Результат для користувача: власна структура категорій і кольори — перегляд, створення,
перейменування, зміна кольору й видалення.

## Рішення

- **Схеми Supabase не змінюються.** Використовуємо те саме, що web (`groups-and-categories-repository.ts`):
  - список — view `groups_with_categories_tx_counts` (`views.sql`): групи користувача без службових, у кожній —
    категорії (`jsonb`) з кольором і **кількістю операцій** (`CAT-02`, `CAT-03`, `GEN-05`);
  - створення — наявні `CategoriesRepository.createGroup` / `createCategory` через
    `AppViewModel.createGroup` / `createCategory` (вони вже перечитують довідкові дані);
  - назва й колір — `update` в `groups` / `categories` за `id` з `select("id")` (порожньо → «не знайдено»). На
    iOS назва й колір змінюються в одному діалозі, тож і запит один (`{ name, color }`); web робить два окремі;
  - видалення — `delete` за `id`, як web.
- **Де живе код.** Новий `Features/Groups`: `GroupsRepository` (список із лічильниками, оновлення, видалення),
  `GroupsViewModel`, `GroupsView`. Створення лишається в `CategoriesRepository` — його вже використовує пікер.
- **Екран (`CAT-01…03`).** Нативний `List` зі секціями — по одній на групу:
  - **заголовок секції**: кольорова мітка, назва, позначка типу (Витрата/Дохід), «N категорій»;
  - **рядки категорій**: кольорова мітка, назва, кількість операцій;
  - останній рядок секції — «Додати категорію» (`CAT-07`);
  - угорі — сегментований фільтр **«Тип операції»: Усі / Витрата / Дохід** (`CAT-01`); вибір зберігається, поки
    користувач у застосунку (як фільтри операцій, `TX-08`);
  - «+» у тулбарі розділу — «Додати групу» (`CAT-04`), як «+» у Гаманці й Операціях (`AppSection.addTitle`).
- **Дії з групою й категорією** — через контекстне меню (довге натискання) і свайп, як прийнято в iOS-списках, а
  не редагування «на місці» як на web (документ дозволяє, розділ 0 «Адаптація до платформи»):
  - **«Змінити»** — діалог назви й кольору (`CAT-05`, `CAT-08`, `CAT-10`): той самий `NamePromptView`, що в пікері,
    з режимом редагування (заповнені назва й колір, кнопка «Зберегти»). «Скасувати» — без змін (аналог ✕ на web);
  - **«Видалити»** — лише коли дозволено: група без категорій (`CAT-06`), категорія без операцій (`CAT-09`).
    Інакше дії немає, а в рядку видно, чому: кількість операцій у категорії, «N категорій» у групі. Кожне видалення
    — з підтвердженням (`GEN-22`, `Q-01`);
  - тип групи після створення не змінюється (`CAT-04`) — у діалозі редагування групи вибору типу немає.
- **Нова група (`CAT-04`).** `NamePromptView` отримує необов'язковий вибір типу Витрата/Дохід (сегменти над назвою);
  у пікері категорій тип, як і зараз, фіксований типом форми. За замовчуванням — тип із фільтра, якщо він не «Усі»,
  інакше Витрата.
- **Повідомлення (`CAT-11`, `GEN-19`).** Успіх — короткий `SuccessBanner` («Групу створено», «Категорію
  перейменовано» тощо), помилка — `failureAlert` із назвою дії й поясненням сервера. Тексти — з web
  (`groups.*Successfully` / `*Failed`).
- **Порожній стан (`CAT-12`).** «Тут поки немає груп. Почніть із першої групи» + «Додати групу». Якщо групи є, але
  фільтр типу нічого не лишає, — порожній список із фільтром, не порожній стан (як `TX-07`).
- **Оновлення інших екранів (`GEN-26`).** Після кожної зміни — новий `AppViewModel.categoriesChanged()`:
  перечитати довідкові дані (пікер категорій, фільтри операцій) і `dataChanged()` (кольори й назви в списку
  операцій). Сам екран перечитує список за `dataVersion`, тож бачить і категорії, створені з пікера.
- **Службові записи (`GEN-05`)** не потрапляють на екран: view їх уже відкидає; на iOS додатково нічого не
  фільтруємо.
- **Відома особливість web, яку відтворюємо:** категорію без операцій, але із запланованим бюджетом
  (`monthly_budgets` посилається на неї без `ON DELETE`), видалити не вдасться — сервер поверне помилку
  зовнішнього ключа, і її покаже `failureAlert`. Записуємо в `ios/TECH_DEBT.md` як питання: чи ховати дію
  «Видалити», чи видаляти бюджети разом із категорією.
- **Демо (`AUTH-10`).** `DemoGroupsRepository` будує список із `DemoData.groups` / `categories`; кількість операцій —
  скільки разів категорія трапляється в місячному шаблоні демо-операцій (усі демо-категорії мають операції, тож
  видалити їх не можна). Оновлення й видалення — no-op; створення, як і зараз, нічого не зберігає.

### 5. Перевірка й документація
- [x] Збірка й тести: `xcodebuild … -scheme Finwaze -destination 'platform=iOS Simulator,name=iPhone 18 Pro' test`.
- [ ] Критерії приймання CAT у симуляторі на локальному Supabase:
  - створити групу витрат «Подорожі» з категорією «Готелі», дати колір — і одразу вибрати її в новій витраті;
  - категорію з операціями видалити неможливо (видно кількість операцій); після видалення всіх її операцій — можна;
  - групу з категоріями видалити неможливо;
  - перейменування й зміна кольору видно в списку операцій;
  - фільтр «Дохід» показує лише групи доходів;
  - кожна дія показує банер успіху або помилку;
  - демо: зміни нічого не змінюють.

  Перевірено (UI-прогони, 28.09.2026) на тестових «Travel S7» / «Hotels S7», які потім видалено: нова група витрат
  із кольором і вибором типу; категорія в ній; перейменування через свайп «Змінити» — нова назва одразу в пікері
  категорій; видалення категорії й порожньої групи з підтвердженням; для категорії з операціями контекстне меню має
  лише «Змінити»; фільтр «Дохід»; банери «Категорію створено» / «Категорію видалено». Ще не перевірено в UI: вибір
  нової категорії у витраті до кінця, зміна й прибирання кольору наявної групи, видалення категорії з бюджетом,
  демо-режим.
